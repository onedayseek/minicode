# 设计

## 对话历史与上下文管理

对话历史是 agent 的全部记忆 —— 模型每一轮看到的就是这个数组的全部内容。
这一层要解决的问题是：窗口有限，而长任务的历史必然超出窗口。

**历史与上下文是两样东西**

- 历史：发生过什么。只增不改，任何时候都完整。
- 上下文：这一轮让模型看到什么。每轮从历史投影出来。

收敛和压缩都不从历史里删东西，只是让这一轮的投影里不放它。一句话：
**模型可以忘记，系统不用真的忘记。**

分开之后，几个原本含糊的问题自动有了答案：恢复会话恢复哪个（历史，投影重算）、
压缩后想看原文去哪找（历史里）、界面上该显示什么（历史）。代价是多一层间接。

**预算作用于下一次请求，而不是上一次**

- 用 API 回传的实测值当预算，会漏掉一整轮：检查预算时，中间执行的工具输出
  已经进了历史，却还没进过任何一次请求。这不是 provider 不给用量时的兜底问题，
  正常返回用量时同样发生。
- 所以每轮先渲染出投影，再估算这一份即将发出的请求，估算范围包括工具 schema ——
  它不在消息数组里，却是每次请求都要发的固定开销。
- 实测值改作校准：用「实测 token ÷ 本次字符数」更新估算系数。比硬编码一个除数
  可靠 —— 中英文比例和分词器能让这个系数差出一倍，而它每轮都能免费拿到。
- 拿不到用量时估算照常工作，但界面上标明未经校准。不标的话，一个纯靠猜的数字
  和实测数字长得一模一样。

**两个治理动作使用不同触发条件**

- 工具输出达到绝对体量后就开始收敛。它们可以重新获取，早一点清理主要降低成本和注意力噪声。
- 交接压缩只看 active context 占真实窗口的比例。它有信息损失风险，因此推迟到窗口的中高位。
- 硬停判断 active context 加本次动态输出预算是否真正装不下；清理与交接压缩都在硬停之前。
- 默认按 DeepSeek V4 Flash 配置为 1M 窗口和 384K 输出；窗口与输出上限都可由环境变量覆盖，
  输出上限不小于窗口或窗口低于项目支持下限时直接拒绝启动。换用其他模型时由用户按官方限制设置。
- 最大输出配置表示模型能力上限，不从窗口中永久扣除。每次请求按剩余窗口和安全余量动态收紧实际输出上限。

**两级收敛，低损失的先做**

判据是**能不能重新拿到**：

- 工具输出（读过的文件、搜索结果、命令输出）全都能重新拿到，丢掉不损失任何
  拿不回来的东西。所以先收敛它们，只保留开头并附上「需要时请重新调用」。
- 用户提过的约束、试过什么失败了、为什么否决了某个方案，只存在于对话里。
  这些要留到最后。
- 收敛之后重新估算，仍然超标才做交接压缩 —— 后者要花一次模型请求，而且是有损的。
- 同样按这条判据，工具输出不外置到独立文件再配一个取回工具：输出全都可重新获取，
  重跑一次比维护一套外置存储便宜。

两级的参数要错开。保护范围（收敛不动最近几组）和压缩切点（保留最近几组）若是
重叠，两级会互相挡住 —— 该收敛的工具输出恰好落在保护区里，压缩又够不着它们。

**压缩产出的是交接状态，不是摘要**

- prompt 给固定栏目：任务目标、用户明确的约束与禁令、已完成、关键决策及理由、
  相关文件及各自为何重要、验证情况、下一步。
- 不说「请总结」。自由发挥的摘要会写成「用户让我改 UI，我改了几个文件，跑了测试」
  —— 读着完整，但接手的人没法据此继续。固定栏目强制它回答「接下来干什么」和
  「什么不能碰」，而这两样最容易丢、丢了损失最大。
- **可靠性主要来自栏目设计，不是模型能力**，而这个设计成本几乎为零。
- 滚动进行：旧交接状态连同其后的新历史一起送去，要求整合仍然有效的信息。既不是
  每次从头重新总结（旧细节早已不在上下文里），也不是只总结增量（那样旧约束会丢）。
- 以助手身份进上下文，不用系统身份 —— 那等于把模型自己生成的旧文本提升到系统
  指令的权限层级，后面的用户指令就压不住它了。
- 切点必须落在消息组边界上，否则投影里会出现没有声明的孤儿工具结果。
- 压缩请求不带工具定义：模型可能返回工具调用，而这次请求不在主循环里，
  那组调用永远不会有结果。
- 压缩请求沿用 LLM 客户端的有限重试；重试耗尽或降幅不足时停止当前任务，不发送未经压缩的大请求。

**分层阈值**

- 收敛工具输出：active context 达到绝对阈值后执行，低损、优先。
- 交接压缩：active context 达到真实窗口的七成后执行，有损、靠后。
- 硬停：兜底，不是策略。

**会话持久化**

每次运行把事件流写成 JSONL：用户输入、模型回复（含工具调用与 token 用量）、
工具结果、框架提示、收敛、交接状态、内部异常和终止原因。两个用途：

- 可观测。终端上的显示是截断过的，排查问题需要知道模型实际收到和产生了什么。
- 可恢复。`--resume` 从这份记录重建历史继续工作，中断或换机器都能接上。

恢复的是完整历史加投影状态，两者分别重建 —— 收敛和交接状态都是记录而非销毁，
所以恢复出的上下文与中断前一致，而原文一条不少。

请求事件记录投影形状和估算值，并在首次请求保存完整系统提示与工具 schema；用户、助手、工具结果等事实事件始终完整保存。斜杠命令单独记为 command 事件，不进入模型历史。

## 工具的定义与本地执行

工具是 agent 与真实环境之间的唯一接口。这一层的设计决定了模型能做什么，
以及它需要自己搞清楚多少事情。

**工具粒度：六个专用工具，而不是一个 shell**

理论上给一个 shell 就能覆盖全部能力。拆成 `read_file` `write_file` `edit_file`
`list_files` `grep` `shell` 的理由：

- 输出格式可控。带行号返回的读取让模型引用位置更准。
- 能在工具层加护栏。read-before-edit、路径越界检查都没法在 shell 里做。
- 权限可按工具粒度审批。读操作直接放行，写和执行才需要确认。

代价是模型的动作空间变大，可能选错工具（该用 `edit_file` 时用了 `sed`）。
六个覆盖「读 / 搜 / 改 / 执行」四类能力，再多就是重复。

**原则一：工具要自我描述**

模型做下一步决策需要的信息，由工具主动给出，而不是等它踩坑之后靠报错去补。

- `shell` 的描述里写明实际的解释器、调用形式、路径风格、超时上限，
  以及「每次调用都是新进程，cd 和环境变量不保留」。这些是写命令时必须知道的，
  同一份代码在不同机器上答案不同，只能在运行时给。
- `read_file` 的输出首行标出文件的编码与行尾符。

不这样做的话，模型只能靠试探。它会花掉真实的步数去试，且每个新会话重来一遍。

**原则二：工具能维持的不变量，不交给模型维持**

- 文件的编码、BOM、行尾符、末尾换行由工具保证：模型看到的永远是 LF 归一化文本，
  写回时按原文件的属性还原。
- 这消除了一类必然失败：文件是 CRLF 时，模型在自己的视图里看不见 `\r`，
  抄下来的多行匹配内容永远对不上，而它无从发现原因。
- 一般化：要求模型跨十几步记住某个字节级属性，等于把正确性押在模型行为上。

**编辑方式：字符串精确替换**

- 行号区间：文件一改行号就失效，多步编辑几乎必错。
- unified diff：模型生成合法 diff 的成功率不稳定，格式一错整个补丁作废。
- `old_str` / `new_str` 精确替换。当前采用。代价是要求逐字符复现空白与缩进，
  匹配失败是最常见的报错。

**执行边界**

- 所有工具只能操作启动时指定的工作目录。
- 写操作和命令执行默认逐次确认，可对单个工具在本会话内免确认。
- 少数明显破坏性的命令额外拦截。这是减速带，不是安全边界 ——
  没有 OS 级沙箱，真正的信任边界是用户在场审批。
- 用户拒绝一个调用后，本组尚未执行的调用全部记为取消并立即交回模型；协议上的
  工具结果组保持闭合，但不会在用户已经否决计划后继续执行剩余动作。
- 每个工具调用都带一个必填、独立的 `intent` 元参数，由作出调用决策的主模型生成并与调用一起展示；
  框架审批前取出它，不传给本地工具。不用第二个模型事后猜测理由，避免意图与实际决策脱节。

## 模型输出的解析

模型的输出是不可信输入。解析层的职责是把它变成一次结构化的工具调用，
或者变成一条模型能据以修正的错误 —— 而不是让整个会话失败。

**容错的程度**

- 修有把握的：代码围栏、多余的尾逗号、值已完整时缺失的结构括号。
- 不补未闭合字符串，也不执行因长度上限或内容过滤而截断的工具调用；
  字符串缺掉的后半段无法可靠推断，补成合法 JSON 反而可能执行半份写入内容。
- 但截断时那段文本本身仍进历史。它已经流到用户屏幕上了，内存里没有的话，
  同一进程的下一轮追问会凭空少一段，而从会话记录恢复时它又会回来 ——
  同一段回复在两条路径上不一致，比单纯丢了更难查。
- 不修拿不准的。修错会得到一个合法但语义不同的调用，那比报错糟得多 ——
  报错至少模型知道要重试，语义漂移会静默地做错事。
- 修不动就把解析错误回灌，让模型重发。

**校验的程度**

- 只查必填字段和顶层类型，不引入 jsonschema / pydantic。
- 模型实际会犯的错只有「字段缺失」和「类型写错」两种，
  为覆盖这两种拉一个重度校验库不划算。
- 校验失败同样走回灌，不抛出。

## 循环终止条件

主循环是一个显式状态机：调模型 → 解析 → 执行工具 → 结果写回历史 → 回到开头。
终止判断集中在循环开头，读代码的人一眼能看到所有会让 agent 停下来的情况。

**三类终止条件，性质不同**

- **任务完成**：模型不再请求工具调用。绝大多数任务的正常出口。这个信号完全由
  模型给出，框架不做二次判断 —— 框架无从知道任务是否真的完成，
  强行加判断只会在模型正确时误伤。
- **资源边界**：步数、耗时、上下文占用各有上限。与 agent 做得对不对无关，
  只防止单次任务无限消耗。触发时提示用户可以继续，因为历史是保留的。
- **行为异常**：agent 在原地打转。

**原地打转的判定**

「打转」有两种形态，判定阈值不同：

- 发出完全相同的调用并重复失败。上一次失败的原因还在，同样的调用不会有不同结果，
  阈值低。
- 同一个工具换着参数反复失败。可能是打转，也可能是正常试探 ——
  连续读三个猜错的路径是探索行为，不该被掐断，阈值高。

**先提示，再终止**

- 判定为打转后不直接停，而是向历史注入一条提示，要求换一种思路或直接说明卡在哪里。
- 只有再次触发才真的终止。直接终止会丢掉本来能自救的情况 ——
  模型收到提示后往往真的会改变策略。
- 提示机会每个任务重新给一次，不跨任务累积。

**一条容易搞错的语义**

命令退出码非零不算工具失败。测试失败、编译报错、搜索无匹配都会返回非零，
而这些输出正是模型要读的东西。若计入失败次数，
「跑测试 → 读报错 → 修 → 再跑」这个最常见的调试循环几轮就会被掐断。

## 错误处理

核心判断是：**这个错误谁能修**。分类决定了框架的反应，也决定了错误信息写给谁看。

**按「谁能修」分四类**

- 模型能修的（路径写错、要替换的内容不存在、命令返回非零）：
  转成工具结果回灌进历史，不中断会话。这是最常见的一类。
- 框架能修的（限流、5xx、连接超时）：退避重试，对模型透明。
- 关闭 HTTP 客户端自身的隐式重试，由框架统一掌握次数；服务端给出
  `Retry-After` 时优先遵从，否则使用带抖动的退避间隔。
- 需要用户介入的（拒绝审批）：记为失败结果，交回模型决定下一步。
- 谁也修不了的（认证失败、余额不足、配置缺失）：立即终止并给出明确指引。

**工具错误回灌，而不是抛出**

- 工具执行的失败大多数是模型能自己修的。抛异常终止会话，
  用户就得重新描述一遍任务。
- 工具分发处兜住所有异常 —— 一个工具出错不该让整个会话退出。

**错误消息的设计原则**

给模型看的错误消息要能指导它的下一步。三条递进的要求：

- **能由工具消除的差异，不要变成错误。** 行尾符不一致本身不该成为一条消息。
- **必须报错时，给出模型能验证的判据。** 匹配失败时返回文件里最接近的行和行号，
  而不是笼统地说「检查一下缩进」—— 后者指向了一个它在自己的视图里无法确认的东西。
- **给出的下一步，模型必须真的走得通。** 指向一条同样受限的路径，
  等于制造一次确定的重复失败：它会照做，然后一模一样地再失败一次。

## 终端呈现

一个原则：**输入完整，输出折中**。

- 状态栏里的「Context」只表示 next active context / 真实模型窗口，不混入累计 API 用量。
- `/status` 展示上下文构成、治理阈值与运行状态；`/usage` 单独展示累计输入、缓存和输出。
- 本地斜杠命令写入会话事件流供复盘，但不进入模型历史。

- 模型写的命令和参数完整显示，不截断 —— 那是用户判断它意图是否正确的依据，
  也是决定要不要批准这次操作的依据。
- Markdown 长段落按终端宽度折行，不允许布局组件用省略号静默丢掉回复尾部；列表标记与
  内联代码使用低对比灰色，避免默认高饱和配色抢过正文。
- 工具输出保留首尾、折叠中段。关键信息通常在开头（命令、配置）
  和结尾（错误摘要、结论），中间是过程噪声。
- 编辑的 diff 用另一套折叠规则：改动行是全部价值，上下文行只用于定位。
  套用「留头留尾砍中段」会留下删除行、砍掉新增行，正好丢掉「改成了什么」。
- 批准前和执行后看到的是同一种视图。编辑的预览直接渲染成 diff，
  而不是并排列出两段原文 —— 审批时要判断的是「这一改对不对」，
  两段原文比对费劲，而 diff 正是执行后会看到的形式。
- 调用摘要行里主参数不带参数名（`edit_file(app.py)`），参数名本身没有信息量。
- 会话记录里存完整内容，终端只负责可读性。

**输入交给成熟的终端输入库，不自己处理**

- 粘贴的多行必须整体成为一次输入，否则会被逐行当成独立命令依次执行。
  这要处理 bracketed paste 转义序列，而各平台的原始输入接口并不一致。
- 顺带拿到输入历史和行内编辑，自己实现这两样还要再写一遍。
- 手动换行绑 Alt+Enter 与 Ctrl-J，不绑 Shift+Enter —— 多数终端不把后者
  与 Enter 区分开，发出的是同一个键码，程序这边收不到差别。
- 终端撑不住时（Windows 下的 MSYS 伪终端、管道输入）降级到逐行读取，
  并明确告知少了哪些能力 —— 否则用户只会发现「粘贴多行怎么变成好几条命令了」。
