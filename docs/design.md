# 设计

## 主循环与终止条件

`while True`：检查终止 → 检查上下文预算 → 调模型 → 解析 → 执行工具并回灌。
不用递归，避免调用栈随步数增长，也便于中断和保存现场。工具串行执行。

终止条件四条并存：模型不再返回 tool_calls（自然终止）、步数 > 40、单任务 > 15 分钟、
同一工具连续失败 3 次。上下文占用 > 95% 也停。

卡死检测是先注入一条提示要求换思路，再犯才终止；提示只注入一次。
命令退出码非零不计入失败次数，否则正常的调试循环会被掐断。

方向：并行执行只读工具。

## 上下文管理

历史即 OpenAI 消息数组。token 用 API 回传的 `usage.prompt_tokens`，不本地估算。

超过 70% 时截短较早的 tool 消息 content，附「可重新调用获取」提示，最近 6 条不动。
只截内容不删消息 —— `tool_calls` 与对应的 `tool` 结果必须成组存在，
按消息裁剪就得以消息组为单位，只改 content 则配对天然完整，且零 LLM 调用。

方向：硬阈值下做 LLM 摘要；压缩前归档完整历史使其可恢复。

## 工具

`read_file` `write_file` `edit_file` `list_files` `grep` `shell`，覆盖读 / 搜 / 改 / 执行。

不只给一个 shell 的理由：输出格式可控（带行号的 read 让模型引用更准）、
能在工具层加护栏、审批可按工具粒度做。代价是动作空间变大、可能选错工具。

贯穿工具层的两条原则：

- **工具要自我描述**。模型下一步决策需要的信息，由工具主动给出，
  而不是等它踩坑之后靠报错去补。
- **工具能自己维持的不变量，不交给模型维持**。行尾符、编码、BOM 这类字节级属性
  由工具保证，要求模型跨十几步记住它们等于把正确性押在模型行为上。

### 命令执行

解释器在启动时解析一次，解析结果既用于实际调用，也生成工具描述 ——
模型看到的是具体的 `pwsh.exe -NoProfile -NonInteractive -Command <command>`
和路径风格，而不是笼统的「执行 shell 命令」。语法规则取决于解释器，模型必须知道是哪个。

不用 `shell=True`：它的语义跨平台不同（POSIX 走 `/bin/sh`，Windows 走 `%COMSPEC%`），
而且对模型完全不可见。显式构造 argv 之后，描述与实际执行来自同一个值，不会不一致。

解析顺序：`MINICODE_SHELL` 覆盖 → Windows `pwsh` / `powershell` / `cmd` →
POSIX `bash` / `sh`。Windows 上选 PowerShell 而非 Git Bash，是为了避免
`/c/...` 与 `C:\...` 两套路径语义并存；需要 POSIX 时用环境变量显式指定。

**不做启动时的可执行文件清单**（rg / pytest / git 是否存在）。PATH 在会话中会变
（venv、conda、nvm），启动时探出的结论会过期，变成"自信地错"。改为命令失败时
从 stderr 识别出缺失的可执行文件并点名 —— 知道了解释器，这个匹配才可靠。

退出码一律上报。曾按命令前缀把 `grep`/`rg` 的 exit 1 当作「无匹配」放过，
但「命令不存在」同样是 exit 1，于是真实错误被静默吞掉，且撞上哪种取决于
minicode 从什么终端启动。非零退出本来就只标记为 warn、不计入卡死检测，
所以直接如实上报没有代价。

超时后连子进程一起杀（POSIX `killpg`、Windows `taskkill /T`），
`subprocess.run` 只抛异常不杀 shell 起的子进程，会留下孤儿继续跑。

### 文件读写

模型看到的永远是 LF 归一化文本，匹配也在归一化文本上做，写回时还原原文件的
编码、BOM、行尾符和末尾换行。`read_file` 输出首行标出这些属性，但那只是可观测性，
模型不需要据此行动。

这解决了一类必然失败：文件是 CRLF 时，`read_file` 的视图里 `\r` 不可见，
模型抄下来的多行 `old_str` 永远匹配不上，而报错还让它「检查缩进」——
指向了一个它在自己的视图里无法验证的东西。

`edit_file` 用 `old_str` / `new_str` 精确替换。行号会因文件改动失效，
unified diff 的生成成功率不稳定。代价是要求逐字符复现空白与缩进。

护栏：read-before-edit、路径限制在工作目录内、原子写、按解释器分组的危险命令拦截、
输出超 30000 字符保留首尾、`grep` 扫描文件数上限。
危险命令黑名单是减速带不是安全边界，真正的边界是用户在场审批。

方向：`edit_file` 分级匹配（空白归一化 → 缩进无关 → 相似度）。

## 输出解析

流式 tool_calls 用 dict 按 index 累积，不用 list —— 部分网关的 index 不从 0 开始，
按下标存会留空洞。`name` 未必在首个 chunk 到齐，不能提前校验。

参数三级处理：直接 `json.loads` → 轻量修复（剥代码围栏、去尾逗号、补括号）→
仍失败则把解析错误回灌让模型重试。schema 校验只查必填字段和顶层类型。

## 错误处理

按谁能修分级：模型能修的（路径错、`old_str` 未命中、命令失败）转成 tool result 回灌；
框架能修的（429、5xx、超时）指数退避重试；需用户介入的暂停询问；
致命的（401、余额不足）立即终止并给指引。

`_dispatch()` 兜住所有异常 —— 一个工具出错不该让整个会话退出。

错误消息不只要 actionable，还要**指向模型能验证的东西**。反例是 `edit_file` 早期的
「注意缩进和空格必须逐字符一致」：真实原因是行尾符，而行尾符在 `read_file` 的输出里
根本不可见，模型照着提示重读文件，第二次仍然发出一模一样的 `old_str`。
一条看似 actionable 的消息把模型推向了它无法自查的方向，制造了一次确定的重复失败。

所以错误消息按这个顺序退化：能由工具消除的差异（行尾符）就不要报错；
必须报错时给出可观测的判据（差在缩进几个空格、差在行尾空白、最接近的是第几行）；
都给不出时如实说没有相近内容，而不是笼统地要它「再检查一遍」。

## 会话记录

每次运行写一个 JSONL 到 `.minicode/sessions/`，一行一个事件：
session_start、user、request、reply（含 tool_calls 与 token 用量）、
tool_result（含完整内容与状态）、stop（含终止原因）。带相对时间戳。

终端上的显示是截断过的，不足以定位问题；记录里存完整内容。
单条事件写失败不影响会话本身。

方向：基于同一份文件做 `--resume`，以及压缩前的历史归档。

`--resume` 按事件顺序重放 session_start / user / reply / tool_result / clear
重建消息数组，恢复工作目录、最后已知的 prompt_tokens，以及已读文件列表
（从 reply 里的调用参数取，否则恢复后 read-before-edit 会挡住所有编辑）。

重建以「消息组」为单位丢弃未闭合的 tool_calls：API 要求 role=tool 的消息紧跟在
带 tool_calls 的 assistant 之后，中断可能只留下一组里的部分结果，此时既要剥掉
assistant 的 tool_calls，也要丢掉这组里已到达的 tool 消息 —— 只做前者会留下孤儿
tool 消息，恢复后第一次请求就被 400 拒绝。

恢复时把来源会话的事件抄进新记录，使每个会话文件自成完整历史，
否则对恢复出来的会话再次 `--resume` 会丢掉更早的历史。原记录不被覆盖。

## 终端显示

输入完整、输出折中。模型写的命令和参数完整显示 —— 那是判断它意图是否正确的依据；
工具输出保留首尾、折叠中段，关键信息通常在开头（命令、配置）和结尾（错误摘要、结论）。

同一套折叠逻辑用在所有工具的显示上。超过 24 行则留头 16 尾 6，
单行超 200 字符也截断。参数值含换行或超过 72 字符时换行独立展开。

状态（步数、上下文占用、token）跟在输入提示符上方常驻。

## 测试

`pytest tests/`。会话重建的测试里带一个 `assert_groups_valid` 断言，
校验重建结果满足 API 的成组约束 —— 这类 bug 不校验就只能等真实请求返回 400。

## 权限

读操作放行，写和执行默认逐次确认（可选本会话对某工具免确认），`--yes` 全放行。
工具只能操作启动时指定的工作目录。

没有 OS 级沙箱或容器隔离，信任边界是用户在场审批。
